Decision: model fin-app's book as a double-entry ledger (transactions + splits, debit-positive integer cents, sum 0 per transaction) and keep every existing feature working through facades, instead of rewriting each consumer.

Alternatives considered: (a) single-entry payments table with an "account" column extended for transfers; (b) a full rewrite of reports/bills/importers onto splits in the same goal.

Rationale: double-entry is required to replace GnuCash (transfers, income, opening balances, reconciliation later). Facades (payments/categories/accounts/payees repos) project a "payment-shaped" transaction — non-null payee, exactly two splits, one EXPENSE and one ASSET/LIABILITY — back to the legacy row shape, so ~280 consumers stayed untouched or changed mechanically, and report totals stayed identical (pinned by a parity test computed from the pre-migration tables).

Consequences: reports and the bills grid ignore non-payment-shaped transactions (multi-split, transfers, income) until a later reporting/budgets goal; natural-sign display negates LIABILITY/INCOME/EQUITY; reconciled ('y') splits block edits/deletes on the ledger and facade paths, but some importer/merge paths still bypass the lock (B41, B67) and must be closed before reconciliation ships.
