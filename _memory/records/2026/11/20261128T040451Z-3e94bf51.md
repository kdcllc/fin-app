Pitfall: behavioural QA of the Tauri desktop app on a developer machine can touch the user's real book, and component tests with mocked boundaries hide integration bugs.

What happened: (1) the app remembers its book path in the tauri-plugin-store settings under the user's config/data dirs, and a real book exists there; a plain `npm run tauri dev` would auto-open and migrate it. (2) Opening the live scratch book with plain `sqlite3` while the app ran unlinked the app's -wal/-shm files and invalidated the run. (3) Page tests pre-seeded `importAccountGuids` and mocked Tauri `invoke`, so they never noticed that the GnuCash Import tree was always empty on a real book (ROOT/placeholder parents filtered out) nor that the xlsx export payload's field names did not match the Rust serde shape.

How detected: QA gate evidence run (native window via tauri-driver + WebKitWebDriver on a private Xvfb display).

How to avoid: launch the app with HOME and XDG_CONFIG_HOME / XDG_DATA_HOME / XDG_CACHE_HOME pointed at a temp dir, pre-seed the isolated settings.json with a scratch bookPath, fingerprint (sha256 + size + mtime) the real book before/after, start the app with its cwd in the scratch dir, read live books only with `sqlite3 -readonly`; capture console errors by injecting a console.error/error/unhandledrejection hook via WebDriver. Add at least one test per UI flow that starts from a real-book-shaped fixture with nothing pre-selected, and one test that sends the real TypeScript payload to each Rust command's deserializer.
